# 项目记忆

## Decision Record: 福利活动领取限额

**日期**: 2026-10-23
**问题**: 群福利由多个余额码或抽奖券码组成，需限制同一账号在同一活动成功兑换的码数，并允许后续调整限额及补发。

### 选项分析

| 选项 | 优势 | 劣势 | 复杂度 |
| --- | --- | --- | --- |
| 每批生成单独限额 | 实现简单 | 补发、混合类型可绕过 | 低 |
| 根据已使用兑换码聚合计数 | 少一张计数表 | 删码会恢复额度，并发需额外串行化 | 中 |
| 活动配置加独立账号领取计数 | 补发和混合类型共享，删除码不丢历史 | 新增表，回退需保留记录 | 中 |

### 决策

**选择**: 独立活动和领取计数，限额1–1000，默认1；同活动余额/抽奖券共享次数。
**理由**: 符合用户已确认的按活动限领，创建后可改并继续补发。
**Trade-offs**: 新增数据库结构；只识别站内账号，不处理多账号同一人。一次成功兑换码计一次，即使该码发放多张抽奖券。

### 影响范围

- backend/migrations/247_redeem_campaign_limits.sql、internal/repository/redeem_campaign_repo.go：活动配置FOR SHARE锁、条件UPSERT；计数、兑换码状态、权益同事务提交。
- backend/internal/service/redeem_campaign.go及兑换流程；frontend/src/components/admin/RedeemCampaignDialog.vue与管理端兑换码页。
- docs/redeem-campaign-limits.md：使用、迁移与回退。旧码不回填活动；删除已用码不返还次数；调低不撤回权益。

### 撤销条件

若改为按自然人、每个奖品类型或时间窗口限制，需重新明确业务口径及迁移。回退旧应用前必须暂停活动码或禁用未用活动码，并保留领取记录；旧版不能执行该限额。

## Glossary

### 福利活动（RedeemCampaign）

- 别名/变体：一场福利、福利批次。
- 定义：共享同一个每账号兑换次数上限的一组余额码和抽奖券码，可由多个生成批次组成。
- 范围：管理员活动管理、兑换码生成及兑换限领；避免将一次生成批次等同于一场活动。
- 来源：2026-10-23用户确认按活动、站内账号限领，余额码和抽奖券码都适用，次数可改。
