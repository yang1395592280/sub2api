## 余额和扣费规则

| 余额 | 字段 | 规则 |
| --- | --- | --- |
| 充值余额 | `users.balance` | 旧余额原值保留，承接原有可用待遇 |
| 签到福利 | `users.checkin_balance` | 签到、签到翻倍和签到风控处理 |
| 臻享礼遇福利 | `users.liyu_balance` | 礼遇抽奖、翻倍和猜大小结算 |
| 管理员赠送福利 | `users.gift_balance` | 管理员充值时可另外赠送，也可单独赠送 |

正常余额消费按后台设置的“充值份额 : 福利份额”抵扣，默认 `2:1`，即福利最多承担总费用的三分之一；不足部分由充值余额支付。例如消费 9，福利净额充足且充值足够时扣充值 6、福利 3；福利净额只有 1 时扣充值 8、福利 1。抵扣顺序为签到、礼遇、管理员赠送，三个来源共享同一抵扣上限。

福利来源允许为负数。可抵扣福利使用三个来源的净额 `max(0, 签到 + 礼遇 + 管理员赠送)`。净额为零或负数时，消费全部扣充值，三个福利来源都不变；净额为正时，最多使用该净正额，只扣正数来源，不继续加深负数来源。例：签到 -5、赠送 5，消费 9 全扣充值；签到 -5、赠送 6，消费 9 扣充值 8、赠送 1。活动负债不由充值清偿，后续同来源奖励先填补欠额，例如签到 -0.5，再签到获得 0.3 后仍为 -0.2。

没有正充值余额时，正福利也不能发起余额消费。设充值份额为 P、福利份额为 W，可消费额度为 `充值 + min(福利净正额, floor8(充值 × W / P))`。单次福利扣款不超过 `floor8(费用 × W / (P + W))`、福利净正额、`floor8(当前正充值 × W / P)` 三者的最小值。金额保留 8 位精度，福利上限向下截断，微额消费不得突破补贴上限。已交付请求沿用项目原有后付费透支行为，但不能因此放大福利补贴。订阅消费继续走订阅配额。

后台“签到与风控 → 消费福利抵扣比例”可独立设置 P（1–10000）、W（0–10000），仅接受整数；W=0 关闭消费抵扣。接口为管理员 `GET/PUT /admin/checkins/wallet-policy`，策略存现有 settings 的 `wallet_usage_policy` JSON，缺失时使用默认 2:1，不新增数据库结构。损坏配置会拒绝账务事务，须修复配置后重试。

消费在用户行锁内读取数据库策略，避免多实例缓存不一致。余额准入与在途预留采用充值余额作保守判断，实际账务按上述比例抵扣；Redis 余额键改为 `billing:paid-balance:`，隔离旧版本含福利的额度缓存。因此并发预留可能比界面总可用额度保守。

异步图片先按来源冻结，冻结时的策略保存在 image_hold 钱包流水 notes 中，结算按该策略与已冻结分项上限扣费，不受后续配置变化影响；空 notes 的历史分账冻结按默认 2:1，分账迁移前的冻结保留旧充值余额结算逻辑。快照同时匹配用户、批次和 API Key，释放与结算不能重复执行。取消时按原来源释放，违规签到冻结退款仍按原清退规则处理。流水和真实扣款同事务保存，使用请求 ID、API Key 和事件唯一约束避免重复入账。

## 签到和活动

- 每日以北京时间重置，同一用户每天只能签到一次、参与一次签到翻倍，数据库唯一约束兜底并发。
- 签到先发 R；翻倍成功再发 R，合计 2R；失败扣 1.5R，最终净收益为 -0.5R。余额不足照常扣入签到福利负数，不碰充值余额。
- 签到创建时拒绝负数、非有限数和越界奖励；翻倍在行锁内基于数据库原始奖励验证输赢差额，服务与账务共享十进制 8 位舍入，防止伪造奖励或微额半单位精度不一致。消费与图片账务入口在开始事务前拒绝负数及 NaN/Infinity 金额。
- 礼遇奖励与活动输赢只记礼遇福利；迁移前未参与翻倍的旧活动记录，升级后参与时也采用福利结算，不追扣已入账的历史奖励。
- 后台“签到与风控”可以配置开关、奖励范围、翻倍开关、成功概率和奖励分档。默认签到和签到翻倍关闭；随机数使用操作系统安全随机源。
- 其他历史入口（注册赠送、旧兑换码、支付促销、推广等）保留原有语义。本次分账涵盖新签到、礼遇和管理员单独填写的福利赠送。

## 自动签到处理

用户页面明确展示自动化领取禁用规则。接口复用站点已配置的 Cloudflare、腾讯或阿里云验证码，并对用户限流；页面令牌与账号绑定、一次使用、30 分钟过期，仅存哈希。隐藏字段命中、令牌缺失/无效/过期/重放时记录安全事件并返回 403，不再继续发奖；是否进入三天观察仍依据下述组合证据，不因单次校验失败直接清退。

风控记录页面令牌绕过、隐藏字段提交和验证码拒绝等事件。固定时间、IP、UA 或单一弱信号不触发清退；验证码配置故障和网络请求错误不作为违规证据。当前自动观察条件为：14 日内跨至少 3 个北京时间自然日绕过页面验证，且至少 3 次隐藏字段提交和 3 次验证码拒绝。管理员也可以填写已核实的证据启动观察。

确认后观察 72 小时，期间奖励正常可用；后台任务每分钟检查一次，到期清退剩余正签到福利并暂停签到及翻倍。负签到欠额保留，充值、礼遇及管理员赠送不受影响，已经消费的奖励不追扣。观察期不会向用户暴露内部证据；清退后用户可看到原因、金额和处理编号。

未消费的图片冻结签到福利在释放时继续清退；管理员撤销观察、复核恢复均有记录，恢复只返还实际清退金额，重复执行不重复返还。

观察中的账号被删除时，自动撤销该账号的观察记录，不阻塞其他账号的到期处理。

限制：此规则识别已取得的违规证据，无法可靠识别所有模拟正常浏览器的脚本。未启用验证码时，自动组合证据条件不会完整成立，需要管理员根据核实证据处理。

## 用户与管理员页面

- 仪表盘和个人中心分别展示充值余额、福利余额、三个福利来源及当前可消费额度。
- 消费列表、汇总和 CSV 展示实际充值消耗与福利抵扣。旧记录或尚未完成结算的记录保持未分类，不按当前余额推测历史扣款。
- 管理员用户余额弹窗支持只充值、只赠送及同时操作，充值和赠送在同一事务入账。累计充值和推广返佣只计算充值部分；福利不计入。
- 管理员余额历史包含签到、翻倍、清退、恢复和赠送流水，保留金额来源及操作者。

## 迁移、上线与回退

1. 上线前备份数据库，先在预发布数据库验证迁移及回退操作。暂停新增活动操作，排空正在处理的扣费任务；避免新旧服务同时写钱包。
2. 使用项目现有迁移机制按顺序执行 `251_welfare_wallet.sql`、`252_user_checkin.sql`。两份迁移只新增结构，三个福利字段默认 0，旧 `balance` 和 `frozen_balance` 不改值。
3. 同步发布后端和前端，按项目原有方式清理旧鉴权、余额缓存。启动后核对旧用户充值余额、历史冻结任务和钱包流水，再在后台开启签到与翻倍。
4. 验证 9 = 充值 6 + 福利 3、没有充值无法使用纯福利、负签到欠额恢复、重复请求不重复扣款，以及图片取消原路释放。
5. 本次净额与比例升级无新增 DDL。默认比例保持 2:1；上线应同步更新前后端、停止旧写入实例。核对净福利非正时全扣充值、福利不足封顶、3:1 保存后生效、0 关闭抵扣，以及改比例前已冻结任务按原比例结算。充值准入键已隔离旧缓存，其他鉴权缓存仍按原发布流程刷新。

回退时先关闭签到、礼遇和新增赠送，停止新版本写入并结清新钱包图片冻结，再备份 `users` 三个福利字段、`wallet_transactions`、`wallet_image_holds`、签到记录与风控记录。可以保留新增表列运行旧版，但旧版不识别福利，且其活动可能再次写入充值余额，因此相关活动必须保持停用。恢复新版前必须核对回退期间发生的充值与消费。禁止直接把福利并入充值余额或删表删列，也不能用旧数据库快照覆盖上线后的真实充值。

若仅回退本次比例升级，先将比例恢复 2:1 并排空按其他比例冻结的任务，再停新实例、清理旧余额及鉴权缓存后启动旧版；保留策略和所有钱包流水。旧版仍存在福利净额校验缺陷，回退前必须评估这一已知风险。

本次开发只在隔离的 PostgreSQL/Redis 测试环境执行迁移，没有操作生产库，没有推送或部署。
