# 臻享礼遇设计

## 背景

sub2api 当前已有用户余额、充值、管理员调账、余额历史和用量统计能力。`臻享礼遇` 是一个基于站内余额的运营活动：用户支付固定门票参与一次礼遇，系统按后台配置的概率发放站内余额奖励。活动目标是在可审计、可控风险的前提下，让部分用户获得正向收益体验，同时通过概率配置让系统整体保持略微盈利。

本功能不涉及提现、现金兑换或站外资金流转，所有支出和收入都以站内余额记账。

## 目标

1. 提供用户端独立菜单 `臻享礼遇`，让符合条件的普通用户参与活动。
2. 后台可控制活动全局开关，并支持在全局关闭时单独授权指定用户参与。
3. 后台可配置门票金额、最低参与余额、每日次数上限和奖励档位概率。
4. 每次参与严格按当前启用档位概率独立随机，不做用户级暗控或每日奖池配额。
5. 完整记录每次参与的扣门票、派奖、余额变化和概率快照。
6. 提供用户每日统计、系统每日汇总和奖项命中率偏差统计。
7. 提供后台可视化模拟器，用于批量模拟和按目标利润率反推概率方案。
8. 所有关键校验在后端完成，防止前端篡改、重复请求、并发点击和绕过开关。

## 非目标

1. 第一版不支持提现或现金兑换。
2. 第一版不做用户级个性化概率、黑白名单概率或动态暗控。
3. 第一版不做每日奖池配额锁定。
4. 第一版不自动替运营修改正式配置；模拟器推荐方案需要管理员确认后应用。
5. 第一版不把模拟结果写入真实用户余额、真实流水或真实统计。

## 核心规则

### 可见性和参与资格

用户可见 `臻享礼遇` 菜单的条件：

- 全局开关开启；或
- 当前用户被单独授权。

用户真正可以启动一次礼遇时，还必须同时满足：

- 已登录。
- 用户角色为普通用户。
- 用户状态正常。
- 全局开关开启或当前用户被单独授权。
- 用户余额大于最低参与余额，默认 `> 10` 元。
- 当天参与次数小于每日次数上限，默认 `5` 次。
- 活动配置有效，至少存在一个启用奖项，且启用奖项概率总和为 `100%`。

余额不足时仍显示菜单，但页面提示用户余额需大于最低参与余额才可参与。

### 计费和派奖

- 门票金额默认 `2` 元，后台可配置。
- 用户每启动一次礼遇，系统先扣除门票。
- 系统按后台当前启用奖项概率独立随机命中一个奖项。
- 命中奖励即时加到用户站内余额。
- 用户单次净收益 = `奖励金额 - 门票金额`。
- 系统单次收入 = `门票金额`。
- 系统单次支出 = `奖励金额`。
- 系统单次利润 = `门票金额 - 奖励金额`。

### 概率口径

抽奖采用每次独立随机：

- 每次请求按当时后台配置的启用奖项概率抽取。
- 不按用户输赢历史调整概率。
- 不按每日总次数预分配奖池。
- 长期样本的实际命中率应接近配置概率。
- 后台统计展示配置概率、实际命中率和偏差。

## 后台配置

新增后台模块 `臻享礼遇运营`，建议包含四个页签。

### 活动配置

配置项：

- 全局开关，默认关闭。
- 门票金额，默认 `2`。
- 最低参与余额，默认 `10`，判断口径为余额必须大于该值。
- 每人每日次数上限，默认 `5`。
- 单独授权用户列表。

授权列表能力：

- 按邮箱、用户名或用户 ID 搜索用户。
- 添加授权。
- 取消授权。
- 查看授权时间、授权人、备注。

### 奖项概率

奖项档位不固定，后台可增删改。

每个奖项包含：

- 奖项名称。
- 奖励金额。
- 概率。
- 是否启用。
- 排序。

校验规则：

- 奖励金额必须大于等于 `0`。
- 概率必须大于等于 `0`。
- 至少一个启用奖项。
- 启用奖项概率总和必须等于 `100%`。
- 活动全局开启前必须校验配置有效。

页面辅助指标：

- 单次理论支出 = `SUM(奖励金额 * 概率)`。
- 单次理论利润 = `门票金额 - 单次理论支出`。
- 理论利润率 = `单次理论利润 / 门票金额`。

### 数据统计

支持按日期范围查看：

- 系统总参与人数。
- 系统总参与次数。
- 系统总门票收入。
- 系统总奖励支出。
- 系统净利润。
- 系统利润率。
- 各奖项命中次数。
- 各奖项实际命中率。
- 各奖项配置概率和偏差。

支持用户维度每日统计：

- 用户 ID、邮箱、用户名。
- 日期。
- 当天参与次数。
- 当天门票支出。
- 当天奖励收入。
- 当天用户净收益。

### 模拟器

模拟器在后台页面可视化操作，且不写真实余额和真实流水。

输入项：

- 模拟用户数。
- 每人参与次数，或每人参与次数范围。
- 初始余额，或初始余额范围。
- 门票金额。
- 最低参与余额。
- 每日次数上限。
- 奖项金额和概率。
- 目标利润率。

输出项：

- 模拟总参与次数。
- 模拟总门票收入。
- 模拟总奖励支出。
- 模拟系统净利润。
- 模拟系统利润率。
- 用户盈利人数。
- 用户亏损人数。
- 用户持平人数。
- 最大盈利用户。
- 最大亏损用户。
- 各奖项命中次数和命中率。
- 配置概率和实际命中率偏差。

反推概率能力：

- 管理员输入目标利润率。
- 系统基于门票金额和奖项金额计算目标单次期望支出。
- 生成一组或多组满足概率总和为 `100%` 的推荐概率方案。
- 每组方案展示理论利润率和一次模拟结果。
- 管理员可选择将方案应用到正式奖项配置。

## 数据模型

建议新增独立表，避免污染现有支付订单和 usage 统计。

### zenxiang_liyu_settings

活动配置表，也可复用现有 `settings` 键值表存储 JSON。若后续配置项和审计需求较多，建议独立表。

建议字段：

- `id`
- `global_enabled`
- `ticket_amount`
- `minimum_balance`
- `daily_play_limit`
- `created_at`
- `updated_at`

### zenxiang_liyu_prizes

奖项配置表。

建议字段：

- `id`
- `name`
- `reward_amount`
- `probability`
- `enabled`
- `sort_order`
- `created_at`
- `updated_at`

### zenxiang_liyu_user_grants

用户单独授权表。

建议字段：

- `id`
- `user_id`
- `enabled`
- `granted_by`
- `notes`
- `created_at`
- `updated_at`

约束：

- `user_id` 唯一，避免重复授权行。
- 查询可玩状态时只认 `enabled = true` 的授权。

### zenxiang_liyu_records

每次参与流水表。

建议字段：

- `id`
- `request_id`
- `user_id`
- `play_date`
- `ticket_amount`
- `reward_amount`
- `user_net_amount`
- `system_revenue`
- `system_expense`
- `system_profit`
- `prize_id`
- `prize_name_snapshot`
- `probability_snapshot`
- `config_snapshot`
- `balance_before`
- `balance_after_ticket`
- `balance_after_reward`
- `created_at`

约束和索引：

- `request_id` 唯一，用于幂等防护。
- `(user_id, play_date)` 索引，用于每日次数校验。
- `play_date` 索引，用于每日统计。
- `prize_id` 索引，用于命中率统计。

## 后端接口

### 用户接口

建议前缀：

`/api/v1/zenxiang-liyu`

接口：

- `GET /status`
  - 返回当前用户是否可见、是否可参与、余额、今日次数、次数上限、门票金额、最低余额、不可参与原因和奖项展示配置。
- `POST /play`
  - 发起一次礼遇。
  - 请求体只允许包含幂等请求 ID。
  - 不接收奖励金额、奖项 ID、概率等敏感参数。
  - 返回命中奖项、奖励金额、本次净收益、最新余额和今日剩余次数。
- `GET /records`
  - 当前用户参与记录分页。
- `GET /daily-summary`
  - 当前用户每日汇总。

### 后台接口

建议前缀：

`/api/v1/admin/zenxiang-liyu`

接口：

- `GET /settings`
- `PUT /settings`
- `GET /prizes`
- `POST /prizes`
- `PUT /prizes/:id`
- `DELETE /prizes/:id`
- `GET /grants`
- `POST /grants`
- `DELETE /grants/:user_id`
- `GET /stats/overview`
- `GET /stats/users`
- `GET /stats/prizes`
- `POST /simulate`
- `POST /simulate/recommend`
- `POST /simulate/apply`

## 事务和安全设计

`POST /play` 必须在数据库事务内完成：

1. 校验用户登录、角色、状态。
2. 读取活动配置和授权状态。
3. 校验活动可见和可参与。
4. 校验启用奖项概率总和为 `100%`。
5. 根据 `request_id` 检查是否已有成功流水，已有则返回原结果。
6. 锁定当前用户余额行。
7. 重新校验余额大于最低参与余额。
8. 查询并锁定当天该用户参与次数，或使用事务内统计配合唯一约束防并发超限。
9. 扣除门票。
10. 使用服务端随机数按概率选择奖项。
11. 增加中奖金额到用户余额。
12. 写入参与流水和配置快照。
13. 提交事务。

安全要求：

- 后端是唯一可信源。
- 前端不传奖项、金额或概率。
- 管理员接口必须走后台鉴权。
- 用户接口必须限流，防脚本高频调用。
- 同一用户短时间重复点击不能绕过余额和次数。
- 幂等请求不能重复扣款或重复派奖。
- 日志不得打印敏感 Token 或完整认证信息。

## 前端页面

### 用户端 `臻享礼遇`

页面状态：

- 活动不可见：菜单不出现，直接访问路由返回不可用提示或跳转。
- 余额不足：显示参与门槛和当前余额，不允许点击。
- 次数用完：显示今日次数已用完。
- 配置异常：显示活动维护中。
- 可参与：展示转盘、门票金额、今日剩余次数和奖项列表。

交互：

- 点击 `开启礼遇` 后按钮进入 loading 状态。
- 后端返回结果后播放结果展示。
- 更新余额和今日剩余次数。
- 失败时展示后端原因，不在前端自行判断中奖。

### 后台 `臻享礼遇运营`

后台页面使用页签组织：

- 活动配置。
- 奖项概率。
- 数据统计。
- 模拟器。

页面应突出经营指标，不做营销落地页式布局。

## 统计口径

### 用户每日统计

按 `zenxiang_liyu_records` 聚合：

- `play_count = COUNT(*)`
- `ticket_total = SUM(ticket_amount)`
- `reward_total = SUM(reward_amount)`
- `net_total = SUM(user_net_amount)`

### 系统每日统计

按 `zenxiang_liyu_records` 聚合：

- `participant_count = COUNT(DISTINCT user_id)`
- `play_count = COUNT(*)`
- `revenue_total = SUM(system_revenue)`
- `expense_total = SUM(system_expense)`
- `profit_total = SUM(system_profit)`
- `profit_rate = profit_total / revenue_total`

### 奖项命中率

- `actual_hit_rate = prize_hit_count / total_play_count`
- `rate_diff = actual_hit_rate - probability_snapshot`

统计历史数据时，概率展示应优先使用流水中的概率快照，避免当前配置变化影响历史解释。

## 测试策略

后端测试：

- 配置校验：概率总和、空奖项、负数金额、非法概率。
- 用户资格：未登录、管理员、停用用户、全局关闭、单独授权。
- 余额门槛：余额等于最低余额不可参与，余额大于最低余额可参与。
- 每日次数：达到上限后拒绝。
- 幂等：相同 `request_id` 重放不重复扣款和派奖。
- 并发：同一用户并发请求不能突破次数和余额限制。
- 概率选择：固定随机源下命中奖项可预测，边界值正确。
- 账务：门票、奖励、用户净收益、系统利润和余额变化正确。
- 统计：用户每日、系统每日、奖项命中率聚合正确。
- 模拟器：模拟不写真实流水，目标利润率推荐概率合法。

前端测试：

- 用户菜单可见性。
- 余额不足、次数用完、活动关闭、可参与状态。
- 参与成功后展示结果并刷新余额和次数。
- 后台配置保存校验。
- 奖项概率总和提示。
- 模拟器输入、运行和结果展示。

验证命令建议：

- 后端：`go test ./internal/service ./internal/handler ./internal/repository`
- 前端：`pnpm test --run`

## 风险和注意事项

1. 该功能具有运营收益属性，必须确保概率、流水和统计可审计。
2. 如果未来站内余额支持提现或站外兑换，需要重新评估合规风险。
3. 并发和幂等是核心风险，不能只依赖前端禁用按钮。
4. 概率配置变化会影响后续请求，历史统计必须依赖流水快照。
5. 模拟器只能辅助评估，真实结果会受样本量波动影响。
