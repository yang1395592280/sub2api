# 专属分组用户用量对比设计

## 背景

分组管理当前已有“查看用户”入口，但用户希望它只服务于专属分组，并在查看分组下用户时直接看到每个用户在该分组内的使用情况。展示口径对齐账号管理里的今日统计，不引入新的费用定义。

## 目标

- 只有专属分组显示“查看用户”功能。
- 查看用户弹窗中，每个用户展示今天和昨天两天的用量。
- 今天和昨天在同一用户块内上下排列，方便直接对比。
- 指标口径沿用账号管理：
  - `requests`：请求数。
  - `tokens`：Token 用量。
  - `cost`：账号口径成本，页面可用 `A $xx.xx` 表示。
  - `user_cost`：用户/API Key 扣费口径，页面可用 `U $xx.xx` 表示。
- 聚合范围必须限定在当前分组和当前用户，即 `group_id + user_id + 日期窗口`。

## 非目标

- 不做用户请求明细列表。
- 不做近 7 天、近 30 天或自定义时间范围。
- 不改变账号管理现有统计口径。
- 不给普通分组增加用户用量对比入口。

## 页面草图

```text
查看用户 - 专属分组 A

sub2api
余额 $24.9162
更新于 2026/06/26 19:54:14

今天  2026/06/26
2.6K req     232.9M token     A $281.55     U $41.79

昨天  2026/06/25
1.9K req     180.2M token     A $210.30     U $35.12
```

## 推荐方案

新增一个分组用户用量聚合接口，由后端一次性返回当前分组下当前页用户的昨天和今天统计。前端在“查看用户”弹窗加载成员后，按用户 ID 批量请求用量并展示。

推荐这个方案的原因：

- 避免前端对每个用户逐个请求，减少接口数量。
- 聚合逻辑集中在后端，字段口径和账号管理一致。
- 前端只负责展示，不重复实现统计规则。
- 后续若需要排序或分页统计，可以在同一接口上扩展。

## 备选方案

1. 前端复用已有用量接口并按用户逐个请求。
   优点是后端改动少。缺点是接口数量随用户数增长，弹窗打开会慢，且更容易产生统计口径分散。

2. 直接在现有分组成员接口中追加用量字段。
   优点是前端只请求一次。缺点是成员列表接口职责变重，普通成员查询也会被用量聚合拖慢，不利于后续维护。

## 后端设计

新增接口建议：

```text
GET /api/v1/admin/groups/:id/users/usage-comparison
```

请求参数：

- `user_ids`：逗号分隔的用户 ID 列表，建议前端传当前页成员 ID。
- `tz`：可选时区，默认使用系统现有 `timezone.Today()` 口径或前端传入的本地时区。

响应结构建议：

```json
{
  "group_id": 1,
  "today": "2026-06-26",
  "yesterday": "2026-06-25",
  "stats": {
    "123": {
      "today": {
        "requests": 2600,
        "tokens": 232900000,
        "cost": 281.55,
        "standard_cost": 250.1,
        "user_cost": 41.79
      },
      "yesterday": {
        "requests": 1900,
        "tokens": 180200000,
        "cost": 210.3,
        "standard_cost": 198.4,
        "user_cost": 35.12
      }
    }
  }
}
```

统计 SQL 口径与账号管理今日统计一致，只是增加用户和分组维度：

- `COUNT(*) AS requests`
- `SUM(input_tokens + output_tokens + cache_creation_tokens + cache_read_tokens) AS tokens`
- `SUM(COALESCE(account_stats_cost, total_cost) * COALESCE(account_rate_multiplier, 1)) AS cost`
- `SUM(total_cost) AS standard_cost`
- `SUM(actual_cost) AS user_cost`
- `WHERE group_id = $groupID`
- `WHERE user_id = ANY($userIDs)`
- 日期范围分别限定为昨天和今天。

接口需要校验：

- 分组存在。
- 分组是专属分组，即 `is_exclusive = true`。
- 用户 ID 为空时返回空统计。
- 无记录用户返回零值统计，方便前端稳定渲染。

## 前端设计

分组管理页面调整：

- 操作列中，“查看用户”仅在 `row.is_exclusive === true` 时显示。
- 普通分组不显示该按钮。

成员弹窗调整：

- 保持现有用户基础信息展示。
- 对当前页用户批量加载昨天/今天用量。
- 每个用户展示两行：
  - 今天：`req`、`token`、`A $cost`、`U $user_cost`
  - 昨天：同样字段。
- 数字格式复用账号管理：
  - 请求数用紧凑格式，例如 `2.6K req`。
  - Token 用 `K/M/B` 紧凑格式。
  - 金额使用现有 `formatCurrency` 或同等格式。
- 加载中展示骨架或灰色占位。
- 接口失败时，不影响成员列表展示，用短错误提示替代用量块。

## 数据流

1. 管理员进入分组管理。
2. 只有专属分组显示“查看用户”。
3. 管理员点击“查看用户”。
4. 前端加载当前分组成员。
5. 前端收集当前页用户 ID，请求分组用户用量对比接口。
6. 后端按 `group_id + user_id + 昨天/今天` 聚合 `usage_logs`。
7. 前端按用户 ID 合并统计并展示上下两行对比。

## 错误处理

- 分组不存在：返回 404。
- 非专属分组请求该接口：返回 400 或 403，并提示该功能仅支持专属分组。
- 用量查询失败：前端保留用户列表，显示用量加载失败。
- 部分用户无用量：显示零值，而不是空白。

## 测试建议

后端：

- 专属分组下多个用户，今天和昨天统计正确。
- 同一用户其他分组用量不被统计进来。
- 同一分组其他日期用量不被统计进来。
- 普通分组调用接口被拒绝。
- 无用量用户返回零值。

前端：

- 专属分组显示“查看用户”，普通分组不显示。
- 弹窗中今天和昨天上下排列。
- 请求数、Token、A 成本、U 用户消费金额格式符合账号管理口径。
- 用量接口失败时成员列表仍可查看。

## 风险与注意事项

- `usage_logs` 可能数据量较大，查询必须带 `group_id`、`user_id` 和时间范围，避免全表扫描。
- 日期边界要与现有后台统计口径一致，避免跨时区导致今天/昨天不一致。
- 页面不应把 `cost` 和 `user_cost` 文案写反；`A` 对应账号口径成本，`U` 对应用户扣费口径。
