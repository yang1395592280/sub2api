# 臻享礼遇幸运金币与用户明细设计

## 目标

本次改动包含两个相互独立但同属臻享礼遇模块的需求：

1. 幸运金币未命中时降低用户损失。原始奖励为 `R` 时，最终净奖励从 `-R` 调整为 `-0.5R`。
2. 管理员在“甄选运维 > 用户统计”中点击用户邮箱，可在当前行下方查看该用户在所选统计日期内的逐次抽奖明细。

## 幸运金币结算

抽奖成功后，原始奖励 `R` 已计入用户余额。幸运金币的调整额按结果计算：

- 命中：调整额为 `+R`，最终净奖励为 `2R`。
- 未命中：调整额由 `-2R` 改为 `-1.5R`，最终净奖励为 `R - 1.5R = -0.5R`。

例如原始奖励为 `1`：

- 命中后余额累计增加 `2`。
- 未命中后余额累计减少 `0.5`。

调整额继续写入 `lucky_coin_adjustment`，并沿用现有方式同步更新用户余额、`user_net_amount`、`system_expense` 和 `system_profit`。接口字段及结果枚举保持不变，未命中结果仍使用 `zero`，避免不必要的契约和历史数据兼容改动。

数据库现有不可变触发器只允许未命中调整额等于 `-2R`。新增前向迁移，用 `CREATE OR REPLACE FUNCTION` 将允许值更新为 `-1.5R`。不得修改已执行的 `180_zenxiang_liyu_lucky_coin_mutation_allowlist.sql`，也不追溯修改已经完成幸运金币结算的历史记录。

## 管理员用户抽奖明细

### 接口

新增管理员接口：

```text
GET /admin/zenxiang-liyu/stats/users/:user_id/records?date=YYYY-MM-DD&page=1&page_size=20
```

接口受现有管理员路由鉴权保护。参数规则：

- `user_id` 必须是正整数。
- `date` 必须使用 `YYYY-MM-DD`，并与用户统计页当前选择的日期一致。
- `page` 和 `page_size` 沿用项目通用分页解析与臻享礼遇分页上限。

服务层新增管理员按指定用户和日期查询记录的方法，仓储层复用现有 `ListUserRecords` 查询，不复制 SQL。响应继续使用现有 `ZenxiangLiyuRecord` 和分页响应结构，包含抽奖时间、奖品、原始奖励、幸运金币结果、幸运金币调整额和最终用户净额所需字段。

### 前端交互

用户统计表采用行内展开，不使用弹窗：

- 用户邮箱显示为可点击按钮，并提供清晰的展开/收起图标和可访问状态。
- 点击后在该用户汇总行下一行展开详情；再次点击同一邮箱收起。
- 首次展开时按当前统计日期懒加载明细，避免统计页初始请求一次加载所有用户记录。
- 同一时间只展开一个用户。展开另一个用户时关闭前一个用户详情。
- 同一用户、同一日期的成功响应可在当前页面会话内缓存。
- 修改统计日期或重新加载统计页时，收起详情并清空明细缓存，防止展示旧日期数据。
- 请求期间显示加载状态；无记录时显示空状态；请求失败时在展开区域显示错误，并允许再次点击重试。

展开区域使用紧凑表格展示以下列：

1. 抽奖时间。
2. 奖品。
3. 原始奖励。
4. 幸运金币结果：未参与、翻倍成功或未命中。
5. 调整金额。
6. 最终净额，即记录中的 `user_net_amount`。

明细按 `created_at DESC, id DESC` 排序。首期每个用户加载最多 100 条当天记录，与用户统计页现有最多 100 个用户的加载方式一致；当天单用户超过 100 条时保留分页响应能力，但本次界面不增加翻页控件，因为当前活动每日票数限制使该情况不属于正常业务路径。

## 错误与兼容性

- 幸运金币事务中的任一余额或记录更新失败时，沿用现有事务回滚行为。
- 新迁移仅放宽新公式对应的合法更新，不允许修改其他抽奖记录字段。
- 旧记录保留原结算结果，因此历史统计不会被重算；新部署后的幸运金币操作按新公式结算。
- 管理员明细接口不会暴露用户密码、Token 等敏感信息，只返回现有抽奖记录 DTO。
- 前端中英文文案同步更新：幸运金币提示不再描述“扣回并倒扣原奖励”，管理员明细增加必要的列标题、状态和错误文案。
