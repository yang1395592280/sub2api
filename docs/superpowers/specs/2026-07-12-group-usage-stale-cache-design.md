# 分组用量过期可读缓存设计

## 背景

分组管理页会在分组列表加载完成后请求 `/api/v1/admin/groups/usage-summary`，展示每个分组的今日用量和累计用量。当前接口在缓存未命中时聚合全量 `usage_logs`；现有缓存有效期为 5 分钟，过期后会直接删除，因此首次访问、服务重启后访问，以及间隔超过 5 分钟的访问都会同步等待慢查询。

线上只读复现中，分组页从打开到网络空闲约需 10.5 秒。前端列表先完成渲染，而用量列持续显示占位符，瓶颈位于用量汇总接口的冷查询路径。

## 目标

- 缓存曾成功生成后，分组页不再因 5 分钟缓存过期而同步等待全历史聚合。
- 用量数据允许约 5 分钟延迟。
- 同一服务实例内，同一统计日期的并发刷新只执行一次仓储查询。
- 后台刷新失败时继续返回最近一次成功结果，不把短暂数据库故障放大为页面不可用。
- 保持现有 API 路径、请求参数和响应结构不变。

## 非目标

- 本次不新增分组用量预聚合表，不修改 `usage_logs` 写入链路，也不执行历史数据回填。
- 本次不改变今日用量和累计用量的统计口径。
- 本次不承诺服务进程首次启动且完全没有缓存时秒级返回。
- 本次不引入跨实例或跨重启的持久缓存；如后续仍需消除首次冷查询，可另行接入 Redis 或预聚合表。

## 方案

在现有 `DashboardService` 分组用量内存缓存上实现 stale-while-revalidate：

1. **无缓存**：同步调用仓储生成结果。成功后写入缓存并返回；失败则返回现有错误。
2. **新鲜缓存**：缓存年龄小于 5 分钟时立即返回，不访问仓储。
3. **过期缓存**：立即返回最近一次成功结果，并在后台触发刷新。
4. **正在刷新**：其他请求继续返回过期结果，不重复触发仓储查询。
5. **刷新成功**：原子替换缓存结果和更新时间。
6. **刷新失败**：保留旧结果并记录带上下文的错误日志；进入 30 秒重试冷却，避免每个请求都重新压数据库。

缓存条目不再因超过 5 分钟而删除。5 分钟表示“新鲜期”，不是“可读取寿命”。缓存仍按 `todayStart` 隔离，跨日后的第一个请求会使用新日期键，因此会同步生成当天的新条目，避免把上一自然日的 `today_cost` 当作当天数据。

## 组件与数据流

### Service

`DashboardService.GetGroupUsageSummary` 负责判断缓存状态并返回结果：

- 复用现有切片克隆逻辑，避免调用方修改共享缓存。
- 为每个 `todayStart` 条目维护结果、最近成功更新时间和刷新中状态。
- 同步冷查询和后台刷新共用同一套单飞状态；无缓存的并发请求由首个请求查询，其余请求等待同一结果。
- 在锁内只完成状态判断和标记，不在锁内执行数据库查询。
- 后台刷新使用独立的 30 秒超时 context，不能复用 HTTP 请求 context；请求完成后原请求会被取消，复用会导致刷新立即失败。
- 刷新 goroutine 必须通过 `defer` 清除刷新中状态，并处理查询错误。
- 新日期条目写入成功后清理旧日期条目，避免长期运行时缓存 map 持续增长。

### Repository

`GetAllGroupUsageSummary` 的 SQL 和接口保持不变。本次通过避免用户请求同步等待重复全表聚合来改善体验，不调整统计 SQL。

### Frontend/API

前端和 handler 无需改动。接口仍返回完整的 `{ group_id, today_cost, total_cost }[]`，页面继续按现有逻辑展示数据。

## 并发与失败处理

- 同一 `todayStart` 的过期缓存只允许一个后台刷新任务运行。
- 刷新期间的请求全部返回同一份最近成功快照。
- 后台刷新设置 30 秒超时，避免数据库异常时 goroutine 长期占用。
- 刷新失败不更新成功时间，并记录最近失败时间；冷却期内继续返回旧值但不重试，冷却结束后的首个请求可再次触发刷新。
- 无缓存的并发首次请求也应合并为一次仓储查询，避免服务启动后出现缓存击穿。
- 服务关闭不需要等待刷新完成；超时 context 会限制后台任务生命周期。

## 测试与验收

Service 单元测试覆盖：

- 新鲜缓存命中时仓储只调用一次。
- 过期缓存立即返回旧结果，并触发一次后台刷新。
- 多个并发请求命中过期缓存时只触发一次后台刷新。
- 后台刷新成功后后续请求读取新结果。
- 后台刷新失败时旧结果仍可读取，冷却期内不会重复刷新，冷却结束后允许重试。
- 无缓存的并发请求合并为一次仓储查询。
- 不同 `todayStart` 使用不同缓存条目。
- 新日期成功缓存后旧日期条目被清理。
- 返回结果保持防御性复制。

验收时运行 `backend/internal/service` 相关 Go 测试，并检查竞态条件；如本机环境允许，再运行该包的 `go test -race`。由于 API 契约和前端行为不变，不要求新增前端测试。

## 风险与后续

- 服务首次启动或跨日后的第一次查询仍会同步执行全历史聚合，这是本次最小改动方案的已知边界。
- 多实例部署时每个实例仍会各自刷新一次；若实例数量增多，应使用 Redis 分布式缓存/锁或分组预聚合表。
- 过期数据可能在数据库持续故障期间长期保留。日志需包含统计日期、缓存年龄和刷新错误，便于运维识别。
- 全历史 SQL 的成本仍然存在，只是从周期性用户阻塞路径移到单次后台刷新。数据继续增长后，应评估按分组维护累计值或扩展现有聚合体系。
