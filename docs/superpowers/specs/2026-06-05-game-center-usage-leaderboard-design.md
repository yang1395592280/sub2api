# 游戏中心迁移、全站用量排行榜与批量测试耗时设计

## 1. 目标

在当前 `/Volumes/workspace/中转站/sub2api` 项目中，迁移参考仓库 `/Volumes/workspace/中转站/sub2api-大转盘` 的游戏中心能力，并补充两个配套增强：

1. 迁移完整游戏中心体系，包括：
   - 游戏中心总览页
   - 大转盘
   - 猜大小
   - 签到
   - 签到幸运奖励加倍
   - 游戏后台管理能力
2. 新增普通登录用户可见的“全站用量排行榜”，并在首页提供简版预览。
3. 在账号管理的“批量测试连接”弹窗中，为每条测试结果追加单条耗时展示。

本次设计的核心原则是：**游戏积分体系与当前余额体系彻底隔离，不能存在积分与余额之间的互转、复用或隐式耦合。**

## 2. 已确认范围

### 2.1 必做范围

- 迁移 `Game Center` 用户侧主页面。
- 迁移 `Lucky Wheel` 和 `Size Bet` 两个游戏。
- 迁移签到能力，并将签到入口与展示纳入游戏中心。
- 保留签到后的幸运奖励加倍玩法，但奖励改为积分。
- 迁移游戏中心后台管理模块。
- 增加游戏积分台账与后台积分调整能力。
- 新增全站用量排行榜独立页面。
- 在普通用户首页 `Dashboard` 增加排行榜简版预览。
- 在普通用户导航中增加 `Game Center` 和 `Usage Leaderboard` 两个入口。
- 在批量测试连接弹窗中展示每个账号测试耗时。

### 2.2 明确排除范围

- 不迁移“余额兑积分”。
- 不迁移“积分兑余额”。
- 不允许签到奖励进入余额流水。
- 不允许游戏输赢影响余额、订阅额度、充值、返佣、优惠码等现有业务。
- 不做游客可见排行榜；排行榜仅对登录用户开放。

## 3. 推荐落地方案

### 3.1 推荐方案

采用“**完整迁移游戏中心，但改造为纯积分游戏平台**”方案：

- 复用参考项目中已验证的页面结构、玩法流程、后台入口和数据模型。
- 对所有与余额耦合的部分做定向拆除或替换。
- 将签到奖励、签到加倍奖励、游戏奖励、管理员补发统一沉淀到独立积分流水中。
- 全站用量排行榜直接基于当前项目现有 usage 数据聚合，不与游戏数据混用。

### 3.2 选择该方案的原因

- 与用户目标最一致：既要完整游戏中心，又要彻底去余额化。
- 参考项目中已有大部分可复用实现，适合迁移后再做结构性裁剪。
- 后续如果继续增加更多纯积分玩法，此方案扩展成本最低。

页面风格可参考用户给出的示意图：

## 5. 权限与脱敏设计

## 5.1 页面权限

- 游戏中心：登录用户可访问。
- 全站用量排行榜：登录用户可访问。
- 首页排行榜预览：登录用户可见。
- 后台游戏中心配置、积分调整、签到配置、游戏统计：仅管理员可访问。

## 5.2 脱敏规则

全站用量排行榜属于普通用户可见页面，必须强制脱敏。

建议统一脱敏规则：

- `username`：
  - 长度 <= 1：原样展示
  - 长度 2 到 3：保留首字符，其余替换为 `*`
  - 长度 >= 4：保留前 3 位，其余替换为 `*`
- `email`：
  - 保留 `@` 前最多前 3 位
  - 域名可只保留主域简写，或直接不展示域名
- 头像、用户 ID 可不展示

榜单中禁止出现：

- 完整邮箱
- 完整用户名
- 用户 ID
- API Key
- 账号备注
- 分组信息
- 上游平台账号信息

建议实现为统一的榜单 DTO 脱敏层，而不是前端临时截断，避免后端接口被其他页面复用时泄露原值。

## 7. 数据模型设计

## 7.1 复用与迁移原则

优先迁移参考项目已有表结构和服务层，但做以下改造：

- 删除或禁用所有与余额换算有关的表字段和业务分支。
- 所有奖励结算改写到独立积分资产。
- 签到逻辑不再调用余额发放逻辑。

## 7.2 积分资产模型

建议保留或迁移如下核心结构：

- 用户积分字段，例如 `users.points`
- 积分流水表，例如 `game_points_ledger`
- 积分领取记录，例如 `game_points_claims`
- 游戏下注/回合/钱包流水表：
  - `game_rounds`
  - `game_bets`
  - `game_wallet_ledger`
  - `game_rank_snapshots`
- 大转盘开奖记录表
- 签到记录表，例如 `checkin_records`

## 7.3 与当前项目余额体系的隔离原则

以下边界必须成立：

1. 游戏积分不能写入余额字段。
2. 签到奖励不能写入余额流水。
3. 游戏结算不能复用充值、消费、返佣、优惠码等金额流水表。
4. 后台查看用户余额时，不应自动合并游戏积分。
5. 用户任何现有消费逻辑都不能读取游戏积分作为支付来源。

## 7.4 排行榜数据源

全站用量排行榜的数据源来自当前项目现有 usage 日志与聚合能力，不来自游戏中心表。

建议聚合维度：

- 日期
- 用户
- 成功请求次数
- Token 总量

建议榜单统计口径：

- 成功请求次数：仅统计成功请求
- Token 总量：`input + output + cache read + cache creation` 的总 token 数，口径与当前 usage 页保持一致

- `GET /api/v1/game/lucky-wheel/overview`

## 8.2 用户侧全站用量排行榜接口

建议新增独立接口：

- `GET /api/v1/usage-leaderboard/overview`
- `GET /api/v1/usage-leaderboard/items`

查询参数建议：

- `date=YYYY-MM-DD`
- `metric=requests|tokens`
- `page`
- `page_size`

返回内容建议包含：

- 统计日期
- 榜单类型
- Top 3 数据
- 列表数据
- 用户脱敏名称
- 指标值
- 排名

## 8.3 首页预览接口

可选两种实现方式：

### 方案 A：复用完整榜单接口

- 首页直接请求榜单接口并截取前三。

优点：

- 接口少。

缺点：

- 首页拉取数据冗余。

### 方案 B：增加首页预览接口

- `GET /api/v1/dashboard/game-center-preview`
- `GET /api/v1/dashboard/usage-leaderboard-preview`

优点：

- 响应轻量，首页加载更稳定。

缺点：

- 需要多维护两个 DTO。

推荐：**优先采用方案 B**，因为首页通常需要更轻量、稳定且便于缓存。

## 8.4 批量测试连接接口

现有批量测试连接前端已经按账号逐个测试并输出结果。

本次增强不要求新增单独接口，推荐方式是：

- 在前端对每个账号测试前记录开始时间。
- 在收到该账号最终结果后记录结束时间。
- 计算耗时并在输出行中追加展示。

如果当前测试接口已经能返回服务端处理时间，也可以双端结合，但最终以用户看到的端到端耗时为准。

## 11. 错误处理与边界条件

## 11.1 游戏中心

- 游戏开关关闭时，用户页返回空状态而不是 500。
- 签到重复提交时，返回明确已签到提示。
- 积分不足时，大转盘/猜大小返回明确提示。
- 猜大小下注重复提交要具备幂等保护。

## 11.2 排行榜

- 某日无数据时，应返回空榜单状态。
- 日期非法时，返回 400。
- 登录失效时，按普通鉴权处理。

## 11.3 批量测试

- 单个账号测试异常时，不影响后续账号测试。
- 即使失败，也要记录该条耗时。
- 中途取消或关闭弹窗时，避免残留错误状态污染下一轮测试。

## 12. 验收标准

## 12.1 游戏中心

- 登录用户可从侧边栏进入游戏中心。
- 用户可看到当前积分、签到状态、签到加倍状态。
- 用户每天可签到并获得积分。
- 用户可完成签到加倍，奖励仍为积分。
- 用户可正常进入大转盘和猜大小并完成积分结算。
- 游戏中心中不存在余额兑换入口和余额换算文案。

## 12.2 数据隔离

- 游戏积分变化不会影响余额。
- 余额变化不会影响游戏积分。
- 签到记录和游戏流水不会出现在余额流水中。
- 后台积分调整不会写入余额历史。

## 12.3 全站用量排行榜

- 登录用户可访问完整排行榜页面。
- 首页能展示排行榜简版预览。
- 排行榜支持成功请求次数榜和 token 总量榜。
- 排行榜支持按日期查看。
- 榜单中的用户信息已脱敏。

## 12.4 批量测试

- 管理员在账号管理中打开批量测试弹窗。
- 每个账号测试结果后都能看到单独耗时。
- 成功和失败结果均有耗时。

## 13. 风险与权衡

## 13.1 最大风险

参考项目中的签到模块和部分后台流水展示原本与余额体系存在关联。迁移时如果只复制页面或只复制服务层，容易留下隐式耦合，因此必须从服务层与持久化层一并检查。

## 13.2 排行榜性能

如果全站 usage 数据量较大，按天实时聚合可能在高峰时段变慢。首版可以先走实时查询，但接口设计要预留缓存或日汇总扩展位。

## 13.3 菜单与首页拥挤

普通用户菜单和首页模块增加后，需注意不要冲淡当前主业务（API、订阅、用量）的视觉层级。首页预览必须控制在“轻量引流”而不是“主内容替代”。

## 14. 推荐实施顺序

### 阶段 1：积分底座与签到

- 迁移积分数据模型
- 迁移签到与签到幸运加倍
- 打通游戏中心首页与积分台账

### 阶段 2：游戏玩法

- 迁移大转盘
- 迁移猜大小
- 迁移后台管理与统计

### 阶段 3：全站用量排行榜

- 新增榜单聚合接口
- 新增完整榜单页
- 新增首页简版预览

### 阶段 4：账号批量测试耗时增强

- 在现有批量测试弹窗中补充单条耗时展示

这样安排的原因是：

- 阶段 1 完成后，纯积分游戏平台的基础边界已经成立；
- 阶段 2 才能稳定承载玩法；
- 阶段 3 独立于游戏积分，可并行度较高；
- 阶段 4 范围最小，可最后快速收尾。
