# OpenAI 统一调度与控制台优化设计

日期：2026-07-13

## 1. 背景

本设计用于解决当前 OpenAI 账号调度中首字延迟偏高、自动探测反馈失真、高级调度与自动调度规则不一致的问题，同时保持现有二开功能和上游合并能力。

线上最近 6 小时的观测基线：

- TTFT 样本 19,332 个，平均 5.04s，P50 2.97s，P90 7.21s。
- 组 33 开启自动调度后，P50 从 2.90s 上升到 4.55s，P90 从 7.82s 上升到 21.92s。
- 组 82 开启自动调度后，P50 从 3.18s 上升到 4.00s，P90 从 10.94s 上升到 12.09s。
- 自动探测 766 次，同期真实用户请求 3,199 次，探测额外调用约占 24%。
- 账号 12512 的探测 TTFB 约 1.04s，但真实请求 P50 10.94s、P90 26.65s。
- 33 条探测状态中有 9 条延迟超过 6s、5 条超过 15s，但连续慢响应计数全部为 0。

已确认的直接原因：

1. 成功但很慢的探测统一记录为 `probe_success`，不会进入慢响应熔断。
2. 真实请求 outcome 回写在合并后丢失，自动调度无法学习真实用户请求。
3. probe 启动即全量执行、固定周期、按组和账号重复执行，并且不占正常并发槽。
4. 高级调度与自动调度使用两套健康数据和排序规则。
5. 普通 session 粘性过强，慢账号仍会长期承接同一会话。
6. 当前 `first_token_ms` 不包含账号选择、排队和前次失败重试时间，低估用户体感。

## 2. 已确认决策

- 调度倾向采用均衡模式。
- `previous_response_id` 保持强粘性，确保上下文一致。
- 普通 session 使用软粘性，账号明显变慢、排队或错误率升高时允许切换。
- 采用兼容优先边界，保留现有二开外部契约。
- OpenAI 自动调度、高级调度合并为一套健康数据和一套选号策略。
- 渠道监控和分组定时价格刷新继续独立运行，统一调度器只消费结果。
- 自动调度前端采用 B 方案“调度控制台”。
- 先影子运行，再按分组灰度，不直接全量切换。

## 3. 目标

1. 用真实用户请求作为健康判断的主要数据源。
2. 降低慢账号、排队账号和错误账号被选中的概率。
3. 显著改善 P90/P99，同时稳定改善 P50。
4. 将调度热路径查询改成批量读取，控制选择阶段耗时。
5. 将 probe 调用占比降到真实请求的 5% 以下。
6. 保留自动最低价分组、价格保护、overbrush、Compact、模型映射、WS/SSE 和影子账号能力。
7. 新功能关闭时可以立即回到当前高级调度器。
8. 限制对上游高频修改文件的侵入，降低后续 merge 冲突。

## 4. 非目标

- 不改变用户计费公式和倍率结算语义。
- 不删除现有 OpenAI 自动调度管理入口、分组开关或历史数据。
- 不把通用渠道监控看板合并进账号调度器。
- 不保证将上游自身需要 2s 的生成时间压缩到 1s。
- 不对非 OpenAI 平台做同等规模的统一调度改造。

## 5. 总体架构

统一调度分为六个职责独立的组件：

### 5.1 候选过滤器

复用现有账号、分组和模型能力检查，执行不可绕过的硬过滤：

- 账号状态、可调度状态和临时暂停。
- 模型映射、Compact、图片和其他 endpoint 能力。
- SSE、WS 和 passthrough transport 兼容性。
- 账号配额、限流、过期和父子账号健康联动。
- 分组渠道价格上限保护。
- 熔断和 half-open 流量限制。

硬过滤失败的账号不进入软评分，价格或粘性权重不能覆盖硬过滤结果。

### 5.2 健康快照服务

统一健康维度为：

`account + model_family + endpoint + transport`

健康快照至少包含：

- 预测上游 TTFT EWMA。
- 错误率 EWMA。
- 429 和 5xx 比例。
- 连续慢响应、连续错误和连续成功次数。
- 当前熔断状态和冷却截止时间。
- 最近真实请求时间、最近 probe 时间和数据过期时间。
- 样本来源及真实请求、probe 样本数量。

同一物理账号的健康不按业务分组重复存储。分组 priority、价格限制和启用状态在选号时关联，避免相同账号因加入多个组产生多套互相矛盾的健康状态。

选择阶段必须批量获取候选账号的健康快照，并使用短 TTL 本地缓存；禁止逐账号查询状态和 open circuit。

### 5.3 Outcome 记录器

SSE、WS、passthrough、chat fallback 和失败路径统一上报：

- 请求开始到首个内容 token 的端到端 TTFT。
- routing、queue、upstream、retry 分段耗时。
- HTTP 状态码、错误分类和是否发生账号切换。
- 请求模型、最终上游模型、endpoint 和 transport。
- session 粘性命中、逃逸原因和最终账号。

请求热路径先更新当前进程的轻量状态，再写入有容量限制的异步队列。后台批量持久化健康快照和审计事件，不再为每次请求创建独立 goroutine。

队列满或存储异常时不得阻塞用户请求；必须增加丢弃计数和告警，并继续使用最近快照。

### 5.4 均衡选择策略

请求选择顺序：

1. 解析 API Key、自动最低价分组和模型映射。
2. 执行硬过滤。
3. 处理 `previous_response_id` 强粘性。
4. 批量加载健康、负载、等待和价格数据。
5. 计算普通 session 软粘性和候选预测端到端 TTFT。
6. 形成满足延迟预算的候选池。
7. 在候选池内按健康、等待、价格、配额和组内 priority 排序。
8. 从 Top 3 中进行受控均衡选择。
9. 获取并发槽并做一次轻量状态复核。
10. 转发请求并记录 outcome。

均衡模式默认规则：

- Top-K 默认 3。
- 探索流量默认 3%，仅进入健康且未排队的账号。
- 普通 session 原账号继续获得粘性加分。
- 当原账号比最佳候选预测 TTFT 慢 1,000ms 以上，并且慢幅超过最佳候选的 25% 时，允许 session 逃逸。
- 原账号发生排队、熔断、价格超限、429/5xx 异常或错误率超过阈值时，可以直接逃逸，不要求同时满足延迟差。
- 成本只在满足延迟预算的候选内比较。
- half-open 账号不进入普通 Top-K，只进入单探针或受限恢复通道。

精确阈值通过现有设置体系提供默认值和运行时覆盖，但首版不增加按用户或按 API Key 的个性化调度策略。

### 5.5 Probe 协调器

probe 只用于冷账号、长时间无真实样本账号和熔断恢复：

- 按物理账号、模型族、endpoint 和 transport 去重。
- 多分组共享同一探测结果。
- 多实例使用 leader lock 或分布式租约，避免同时全量探测。
- 周期加入 jitter，不在服务启动时形成同步探测风暴。
- 近期真实样本充足时跳过周期 probe。
- 成功探测根据耗时分类为 success、slow 或 severe_slow。
- probe 不得覆盖更新鲜、样本量更高的真实请求结果。
- half-open 每个账号同时最多一个恢复探针。

### 5.6 可观测性与控制面

新增或扩展以下指标：

- `e2e_first_token_ms`
- `routing_ms`
- `queue_ms`
- `retry_ms`
- `scheduler_decision`
- `sticky_escape_reason`
- `probe_request_ratio`
- `outcome_queue_depth`
- `outcome_dropped_total`
- `health_snapshot_age_ms`

原 `first_token_ms` 保持兼容，现有接口不直接改变字段语义；新的端到端指标使用独立字段，避免历史报表混算。

## 6. 数据与兼容策略

### 6.1 外部契约保持

以下内容不删除或重命名：

- `/openai-auto-scheduler/*` 管理 API。
- 全局和分组自动调度开关。
- 现有设置 key。
- 手动 probe 和重置评分操作。
- 自动调度前端路由。
- 现有 score event/state 历史表。

管理接口可以增量返回端到端 TTFT、真实样本数、预测等待、endpoint、transport 和实际调度结论。

### 6.2 健康状态存储

新增独立的统一健康状态存储，以物理账号维度为主，不破坏现有按组 score state 的唯一键和历史查询。

现有 score state 保留为兼容读取和历史审计。管理页面的分组列表通过“分组账号关系 + 统一健康快照 + 分组策略”生成实际调度视图。

新表和新字段只通过新迁移增加，不修改已执行迁移，不复用可能与上游冲突的历史迁移编号。

### 6.3 指标存储

usage log 采用增量字段记录端到端和分段耗时。历史记录保持为空，不做高成本回填。新旧报表明确区分 `first_token_ms` 和 `e2e_first_token_ms`。

## 7. 二开功能影响

### 7.1 OpenAI 自动调度

保留页面、API、设置、分组开关、手动 probe 和重置能力。内部评分改为统一健康快照，后台显示的数据与实际选号一致。

旧 probe 状态不直接迁移为强健康结论。上线后通过 TTL 自然失效，新真实样本逐步接管。

### 7.2 高级调度

保留现有入口和 feature gate。高级调度不再维护独立的进程内账号级 TTFT 作为最终依据，而是调用统一选择策略。关闭统一调度时仍可回退当前实现。

### 7.3 自动最低价分组

保持“先解析有效分组，再在组内选账号”的顺序。最低价分组只决定候选分组，不绕过健康、能力、价格保护和并发检查。

### 7.4 分组定时刷新余额与渠道价格

保持独立 runner 和现有配置。刷新后的 `ChannelPrice`、配额和价格保护状态由统一调度器消费。

该 runner 同步增加物理账号去重、jitter 和多实例 leader lock，避免相同账号因加入多个组而重复刷新。通用渠道监控看板不并入本 runner。

### 7.5 分组价格保护

继续作为硬过滤。价格超过分组上限的账号不得因低延迟、粘性或高 priority 被重新选中。

### 7.6 Overbrush、模型映射和协议能力

- overbrush 的 429 账号切换和 excluded IDs 继续生效。
- 429 同时进入统一健康反馈，但不得重复执行账号切换副作用。
- 模型映射、Compact、图片能力、WS/SSE 和 passthrough 继续先于软评分过滤。
- `previous_response_id` 的账号一致性高于普通 session 软粘性。

## 8. 前端：B 方案调度控制台

前端继续使用现有管理页面路由，页面拆分为四个视图：

1. 概览
2. 账号健康
3. 调度事件
4. 灰度与配置

### 8.1 概览

第一屏展示四个核心指标：

- 端到端 TTFT P50。
- 端到端 TTFT P90。
- 选号耗时 P95。
- probe 调用占比。

左侧保留分组列表，显示启用状态、账号数量和组级 P90。右侧依次展示：

- 当前分组最高优先级异常摘要。
- 端到端 P50/P90 趋势。
- 慢请求来源分解。
- 实际调度排名表。

实际调度排名至少包含账号/渠道、健康状态、模型族、endpoint、transport、预测 TTFT、负载/并发、渠道价和调度结论。

### 8.2 账号健康

提供高密度表格和详情抽屉。表格支持按分组、健康状态、模型族、endpoint、transport 和异常类型过滤。

详情抽屉展示：

- 真实请求与 probe 样本对比。
- 端到端和上游 TTFT。
- 错误率、429/5xx、排队和重试情况。
- 熔断状态、冷却时间和恢复探针。
- 最近调度决策和 session 逃逸原因。
- 手动 probe 与重置状态操作。

### 8.3 调度事件

按请求和账号展示调度决策链，不再只展示原始 probe 事件。支持查看硬过滤原因、候选排名、最终账号、重试切换和 outcome。

### 8.4 灰度与配置

配置分为：

- 全局/分组开关。
- 调度模式和影子模式。
- Top-K、探索比例和 session 逃逸阈值。
- 慢/严重慢阈值和熔断配置。
- probe 周期、jitter 和样本新鲜度。
- outcome 队列与健康快照状态。

危险配置修改必须显示影响范围并二次确认。日常概览不直接铺开全部数值配置。

### 8.5 前端实现边界

当前单文件页面职责过多，实现时拆分为页面容器、概览、分组列表、账号表格、详情抽屉、事件视图和设置面板。API 类型和数据映射集中在现有 admin API 层，组件不直接解释后端状态机。

桌面端保持高密度运维布局；窄屏将分组列表移到内容上方，表格允许受控横向滚动，按钮和长文本不得溢出。

## 9. 异常降级

- 健康快照缺失或过期：使用中性健康状态和现有 priority/负载规则。
- 健康存储异常：降级到当前高级调度器。
- outcome 队列满：不阻塞请求，增加丢弃计数和告警。
- 所有优选账号不可用：沿用现有 excluded IDs、重试和 overbrush。
- half-open：只允许恢复探针或极少受控流量。
- 价格数据过期：价格只停止参与软评分，已明确的价格超限保护继续生效。
- `previous_response_id` 原账号不可用：沿用现有明确失败行为，不静默迁移上下文。

## 10. 灰度与回滚

1. 修复真实 outcome 和 probe 慢分类，但保持新选择策略关闭。
2. 启用影子模式，新旧调度同时计算，只有旧调度实际选号。
3. 对比预测结果、真实 TTFT、价格、错误率和 session 切换率。
4. 选择一个低风险分组启用新策略，观察 30-60 分钟。
5. 稳定后按分组逐步扩大，不直接全量开启。
6. 任一回滚条件触发后关闭分组或总开关，立即回到当前高级调度器。

回滚不要求撤销数据库迁移；新表和增量字段在旧代码路径中保持无害。

## 11. 验收标准

- P50、P90 不得比同时间段对照组恶化。
- 目标 P50 至少下降 15%，P90 至少下降 25%。
- 账号选择阶段 P95 控制在 20-30ms 内。
- probe 调用占真实请求比例低于 5%。
- 429、5xx 相比基线上涨超过 0.2 个百分点时停止灰度。
- `previous_response_id` 上下文错配为 0。
- 价格保护违规选号为 0。
- outcome 队列持续积压或丢弃率超过告警阈值时停止扩大灰度。
- 自动调度、价格刷新、价格保护、自动最低价分组、overbrush、Compact、SSE 和 WS 回归测试通过。

## 12. 测试策略

### 12.1 单元测试

- 真实 success、slow、severe slow、429、5xx 和网络错误分类。
- EWMA、时间衰减、状态 TTL 和样本优先级。
- 硬过滤、延迟预算、成本排序、Top-K 和探索流量。
- 普通 session 软粘性和 `previous_response_id` 强粘性。
- half-open 单探针和冷却恢复。

### 12.2 集成测试

- PostgreSQL/Redis 批量健康快照。
- outcome 异步批量持久化和队列溢出降级。
- Scheduler Snapshot/outbox 与渠道价格更新可见性。
- 多实例 probe/价格刷新 leader lock 和物理账号去重。

### 12.3 请求链路回归

- SSE、WS、passthrough、chat fallback、messages 和图片相关入口。
- 成功、失败、重试、客户端中断和上游超时。
- overbrush、excluded IDs、自动最低价分组和价格保护。

### 12.4 前端测试

- 四个视图的加载、空状态、错误状态和筛选。
- 全局/分组开关、影子模式和危险配置确认。
- 详情抽屉、手动 probe、重置状态和事件链。
- 桌面和窄屏布局无重叠、溢出或不可操作控件。

## 13. 上游合并策略

统一健康、outcome、probe 和选择策略放在独立 service/repository 文件中。上游高频文件只保留薄适配层：

- `openai_account_scheduler.go`：调用统一策略接口，不承载新状态机。
- Forward、passthrough、WS 文件：只调用统一 outcome 接口。
- `openai_gateway_scheduling.go`：保留兼容入口，避免继续堆积实现。
- Wire：复用现有注入点，生成文件只通过代码生成更新。

现有自动调度路由、设置 key 和 API DTO 采用增量字段，避免破坏式重命名。新增迁移使用新的顺序号并保持幂等，不修改已执行迁移。

该边界不能消除未来所有冲突，但可以把主要实现隔离到上游不存在的新文件，将高频热文件的冲突控制在少量接口调用处。

## 14. 实施顺序

1. 指标和 outcome 正确性修复。
2. probe 慢分类、去重、jitter 和恢复通道。
3. 统一健康快照与批量读取。
4. 均衡选择策略与兼容降级。
5. 分组价格刷新任务去重和多实例协调。
6. B 方案调度控制台。
7. 影子运行、分组灰度和线上验收。

## 15. 风险

- 真实请求反馈恢复后，旧 probe 高分账号会快速降权，流量分布可能明显变化。
- 普通 session 允许逃逸后，缓存命中可能小幅下降。
- 新增端到端指标会增加 usage log 写入字段和分析存储量。
- 多实例健康同步存在短暂最终一致性窗口，必须通过本地快速更新和短 TTL 控制。
- 同时修改调度、probe 和页面会扩大一次发布范围，因此实施必须按阶段拆分并保留独立开关。

## 16. 设计自检
