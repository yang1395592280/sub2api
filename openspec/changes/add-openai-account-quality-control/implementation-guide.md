## 2. 页面、接口和模块接线

### 2.1 两页数据流

| 页面区域/操作 | 拟议 API（根路径 /api/v1/admin/account-quality） | 页面行为 |
| --- | --- | --- |
| 监控概览与运行健康 | GET /overview | 全量聚合；区分账号/策略计数与全局预算，不随历史分页少算 |
| 监控策略表 | GET /policies | 分页、模型/状态/来源筛选；不承担全局统计 |
| 单策略 24H 图 | GET /policies/:id/monitor | 默认当前范围/代次；按需展开，避免每行都拉 288 桶 |
| 历史与时隙下钻 | GET /runs | 使用聚合返回范围和时间桶定位，标准分页遍历全部记录 |
| 结果详情 | GET /runs/:id | 点击后按需 include_response；纯文本、脱敏、过期说明 |
| 状态事件 | GET /events | 关联策略/检测记录/管理操作，解释为何隔离或恢复 |
| 全局设置 | GET/PUT /settings | 单一设置表单，expected_revision；与策略保存分开 |
| 账号/来源选择 | GET /targets | 只选合格的自动来源库存，显示共享号池与来源去重 |
| 题目/路由能力 | GET /benchmarks、POST /capabilities | 展示 requested/effective 与 can_probe/can_enforce，不自造模型能力 |
| 保存前预览 | POST /preview | 与保存共用校验；显示旧观察风险、新启控代次与容量缺口 |
| 策略创建/替换/编辑 | POST /policies、PUT /policies/:id、POST /policies/batch-update | 条件不可原地改写；批量事务；保存本身不发模型调用 |
| 手动/到期复测 | POST /runs | 提交 policy_ids，服务端决定诊断或恢复；逐项 queued/existing/skipped |
| 处置 | 取消、归档、release、emergency-disable | 分别解释停测/停控/人工解除，不把解除说成复测成功 |
| 账号管理辅助列 | POST /summaries | 每页最多 100 账号批量读取，不逐行 N+1；配置跳转到独立页 |

首屏并行获取 /overview 与当前页 /policies，互不拼装为同一数据库快照。选中或展开策略才加载 /monitor；展开详情再取正文。配置页只获取必要库存页和所选账号能力，不一次加载全部账号凭据或历史。

页面 URL 可保留 source_group_id、account_id、policy_id、model_id、state 等白名单筛选，便于账号页跳转。后端授权/范围校验仍是最终依据。不同筛选请求使用取消或请求序号防止旧回包覆盖新选择；显示服务端统计时间。

qualityMonitor.ts 当前假定调用方提供完整集合，只按 policy_id/scope_hash 过滤，不检查代次和完整性。正式 24H API 应在 Go 聚合层移植相同时间/状态/分母规则；用共享的输入输出样例对照，而不是浏览器为统计下载全部历史。TS 模块继续用于完整小样本或对照；正式页直接渲染聚合结果。不得为了“复用”在 Go 服务中引入 Node 运行时。

对复制/翻译的文件保留来源、固定提交与修改说明。发布制品须携带对应 Apache-2.0 许可/NOTICE；不是只把声明留在开发仓库。完整映射与已有文件见 [source-reuse](./source-reuse.md)。

### 2.3 后端调用链

提交任务：管理员鉴权 → 校验范围/能力/revision → 同事务保存幂等回包及 queued 任务 → 返回 202。队列受理并不承诺已有预算或检测已执行。

执行任务：认领/租约 → 核验自动开关及资格（手动不受自动开关限制） → 预算预留/账号容量 → 出站前再次核验版本/身份/取消 → 持久化发送意图和消费 → 指定账号调用 → 严格判分 → 同事务保存终态/状态/事件 → 提交后刷新控制快照。网络等待不持数据库事务锁。

真实请求：原始鉴权模式 → 现有授权/倍率/账号硬限制 → 解析账号有效条件 → 批量质量快照 → 隔离过滤 → 原健康阶段内全来源基准池、观察池 → 原排序/抢槽 → 发送前终检。auto 标记贯穿 effectiveKey、备用来源、引用池和 WS 后续 turn；fixed/独立 composite 在质量 I/O 前退出。

## 3. 配置变更的生效规则

所有“立即生效”指持久化提交后、正常依赖环境下最长 5 秒传播目标；已经发送的上游调用不撤销。任何策略规则编辑都递增 revision，并取消旧 revision 未出站任务；已出站任务不能改变当前状态，但应保存真实结果和 state_skip_reason。全局设置不因无关预算/保留编辑重置所有策略代次。

| 操作 | 下一次执行/队列 | 证据与控制 |
| --- | --- | --- |
| 新建策略 | 四开关默认关闭；可显式提交手动任务 | untested；不存在自动检测全账号的副作用 |
| 修改全局默认策略日预算 | 仅新建时复制 | 已有策略、代次和状态不改；批量修改需另行选中并保存 |
| 全局/策略自动 false→true | 合格且两层开启者首次按 now+jitter 排期；隔离者不得早于 cooldown_until | 不推进控制代次，不把开自动当作开控制 |
| 全局/策略自动 true→false | 取消未出站 scheduled/recovery，next_run_at 为空；手动仍可提交 | 保持已有隔离；已出站有界完成，只有版本/代次等仍匹配才应用结果 |
| 修改普通周期/抖动 | 非隔离者重算 now+新间隔+jitter；不补发历史；未出站旧 revision 任务取消 | 同范围/代次，不在保存时重算质量状态 |
| 修改恢复间隔 | 隔离者重算 max(cooldown_until,now)+新恢复间隔+jitter | 不提前解除冷却；不重置已有隔离 |
| 修改阈值 | 无即时补测；下一有效样本按新规则归约 | 不回放历史即时隔离/恢复；同范围/代次已接受的窗口内证据仍可用于下一次归约 |
| 修改证据窗口 | 下轮任务按新 revision；新鲜度立即按新窗口计算 | observing 过期可退出软惩罚；已隔离不因窗口变化解除 |
| 修改最短冷却 | 当前 cooldown_until 保持；后续再次进入隔离时使用新值 | 无保存即恢复或追溯缩短当前冷却 |
| 修改超时/输出上限 | 下一任务使用；旧任务仅存历史，不自动重发 | 不更改题目/评分版本或凭据范围；不在保存时清除隔离 |
| 修改策略/全局日预算 | 出站前重验，无法满足新上限的预留释放并 skipped；已消费不退 | 不以预算耗尽证明恢复；所有来源任务共用 |
| 降低并发/队列上限 | 已运行不抢停、已排队不清空；低于新上限后才接纳下一项 | 不改变质量证据 |
| 全局/策略控制 false→true | 不隐式开启自动；旧任务不应用到新代次 | 推进相应 epoch，投影为 untested；新样本才能产生真实限制 |
| 全局/策略控制 true→false | 不停止手动/自动任务（除非另关自动） | 退出质量门，可继续观察；再次开启建立新代次 |
| 手动解除 | 旧未出站任务取消，可显式提交新诊断 | untested、清计数、推进策略代次；不是复测恢复 |
| 条件/来源上下文替换 | 原子归档旧策略并建新策略；新开关默认关，需明确设置 | 旧任务不得污染新策略；新范围从 untested 建证据 |
| 移出自动库存/来源上下文失效 | 停止任务/控制，取消未出站任务 | 保留历史，推进代次；重新参与不继承旧隔离 |
| 路由身份/模型映射漂移 | 旧范围失效，重新解析；能唯一归一化则新范围排期，否则禁测并提示替换 | 新证据，发生范围冲突时停控提示，不能任选一条旧策略 |
| 归档 | 停自动/控制，新手动拒绝，运行中协作取消 | 保留历史；不能直接复活旧隔离 |
| 紧急停用 | 原子关两全局开关，取消未出站自动/恢复任务 | 成功持久化后退出质量门；数据库写失败不能显示成功 |
| 缩短保留期 | 下一清理批次执行；保留活动任务/当前状态 | 已清理数据无法靠延长保留期找回，表单预览明确说明 |

改普通规则不会改变 scope_hash；输出上限/超时会影响判分有效率，因此需展示规则版本并在只观察阶段校准。若以后把这类规则定义为证据身份的一部分，必须作为新版本显式迁移，不能悄悄更换 hash 规则。

## 4. 预算与证据窗口的容量预览

### 4.1 硬校验与估算

对每策略计算理想失败跨度 `(F-1)*I`、恢复跨度 `(P-1)*R`；W 必须至少为两跨度与 I/R 的最大值。阈值为 1 仍不允许非法周期/过短窗口。硬校验失败不得保存。

普通基础需求为各已配置自动策略 `86400/I` 的和；同时给出两层自动开关实际开启后的需求，避免观察配置期间显示 0 就误判没有未来成本。每策略日额度及全局额度分别比较，不能只查其中之一。理论预算覆盖率为 `min(1,全局日额度/基础需求)`，需求为 0 时为 null。

窗口余量为 W 减理想跨度；预览将抖动、单次超时、排队上限和繁忙延后列为附加风险。它不基于缺失的实际延迟数据给出“必定在某时隔离/恢复”。预算缺口允许保存但显著告警，硬性不支持的范围/窗口/能力仍拒绝。

| 配置示例 | 普通基础量 | 默认预算的含义 |
| --- | --- | --- |
| 1 策略，30min，日上限100 | 48/日 | 尚有手动/恢复余量，但异常调用也计消费 |
| 18 策略，30min，全局1000 | 864/日 | 理论余136，非恢复保留；恢复频率变高后要重新评估 |
| 100 策略，30min，全局1000 | 4800/日 | 理论覆盖20.83%；均摊约144min一次，可能无法在120min窗口稳定累计三错 |
| F=10，I=30min，W=120min | 需要270min理想跨度 | 窗口硬错误；增加预算也不能解决此规则矛盾 |

UI 给出可由管理员选择的调整方向：减少账号/条件数、调整周期与窗口、显式提高日预算。不得自动缩小阈值、延长证据有效期、删策略或调高费用。未知 Token/价格为 null，调用次数上限不等于金额绝对封顶。

### 4.2 必须分开的三个比例

1. 有效答案通过率：passed/(passed+incorrect)，只回答“能判分的作答中对了多少”。
2. 有效判分率：有效答案/已创建任务总数，排队/错误/取消会降低该值。
3. 条件新鲜覆盖率：有新鲜有效证据的合格活动策略/合格活动策略；未配置的模型/effort/传输不被伪算为已覆盖，未配置账号另计。

预算覆盖率是规划值，和以上三个实测比例分别标示。3 对、1 错、56 error 的正确展示为“有效答案通过率75%，有效判分率6.67%”，不能称可用率75%。

## 5. 一条完整的观察、隔离与恢复路径

以下全部为**设计示例时间，未执行真实检测**。账号101同时属于自动来源A和普通固定组B；有效条件为 example-model / Responses HTTP / low / upstream_default，且通过能力校验。规则采用默认3错、30min冷却、10min复测、2对恢复。

| 阶段/时间 | 管理操作或检测结果 | 监控与真实调度 |
| --- | --- | --- |
| 配置 | 从 /targets 选101及有效来源A，预览48次/日，保存策略11 | 未检测；未调用模型，固定组B无新增质量行为 |
| 观察 | 显式手动检测，或开两层自动但保持控制关闭 | 保存回答/用量/观察状态，“仅观察”不会改变用户选路 |
| 09:00启控 | 两层控制开启，产生新代次 | untested；旧三错即使存在也只作为历史，不立即隔离 |
| 09:01 | 当前代次第1次有效incorrect | observing，auto请求在同健康阶段优先其他来源基准池 |
| 09:31 | 第2次有效incorrect | observing；期间unknown/error不增错、不清错 |
| 10:01 | 第3次有效incorrect | quarantined，cooldown_until=10:31；auto匹配请求拒绝101 |
| 10:15 | 手动诊断passed | 历史可看，但冷却未到，不计恢复次数，仍隔离 |
| 10:31 | 冷却后第1次有效passed | recovering，仍拒绝auto匹配请求；固定组B始终沿原逻辑 |
| 10:41 | 第2次有效passed，在窗口内 | 终态/normal/事件事务提交后才放行；仍受基础额度/禁用限制 |

无延迟且无异常时，从第一错到恢复至少经历失败样本间隔、最短冷却和恢复间隔，示例约100分钟。检测排队/预算/错误会延长；“临时隔离30分钟”只表示最短冷却，不保证30分钟后恢复。

若10:41是incorrect，则恢复计数归零、quarantined、重新冷却至11:11；若是error/unknown则不清已有隔离，通过计数继续受窗口限制。若选择人工解除，必须填写原因并置untested，晚到旧结果只存历史，不能伪造“自动恢复成功”。

## 6. 关键边界示例

| 输入/变化 | 必须得到的行为 |
| --- | --- |
| low证据隔离，真实请求有效high | 不跨条件隔离；显示该high范围未配置/未检测，不声称保证其质量 |
| API Key最高倍率0.2，0.1来源为观察，0.3来源正常 | 0.3仍无资格；只能在合法0.1候选中后备或按原基础原因失败 |
| 同账号auto被隔离，fixed请求 | fixed跳过质量I/O，原禁用/真实额度/429保护仍可独立阻止调用 |
| auto内部克隆effectiveKey并切至引用池 | 继续质量门；不得因实际GroupID非空误认为fixed |
| 已有previous_response_id属被隔离账号 | 返回409 QUALITY_SESSION_RESTART_REQUIRED，不把该ID交给另一账号 |
| 只剩观察账号 | 允许后备，不错误报告全部隔离 |
| 所有基础合格候选被质量隔离 | 返回503 QUALITY_NO_ELIGIBLE_ACCOUNTS，不越授权/倍率找其他来源 |
| 账号移出自动库存后重新加入 | 历史保留，新代次untested；新任务重新核验资格 |
| 上游身份变更，而旧worker稍后完成 | 新范围重建证据；旧结果state_applied=false，不恢复或隔离新身份 |
| 恢复结果passed但数据库提交失败 | 不先放行；旧隔离保持，后续按租约/失败记录处理，不自动重放付费POST |
| 控制开启且无可信快照 | auto返回QUALITY_STATE_UNAVAILABLE；不把读取失败当作未检测放行；fixed不读此数据 |
| 数据库不可写时点紧急停用 | 显示失败与最近同步时间，不能报告全实例已停控 |
| 24H内有超过100条历史，第一页仅20条 | 图和卡片使用服务端完整聚合；下钻标准分页，不从第一页重算通过率 |

## 7. 实施顺序与交付出口

详细任务见 [tasks](./tasks.md)，场景见 [验收规范](./specs/account-quality-control/spec.md)。

1. A：定向HTTP桩、严格判分、四表/幂等、手动观察、两页和聚合接口；本地可从配置走到有解释的结果。四开关关闭不读质量表、不改变旧行为。
2. B：自动/恢复、预算/队列/租约、多实例和资格漂移；完成配置变更表的并发/晚到结果验证，不能用进程锁代替数据库约束。
3. C：精确条件全链路、Codex HTTP/WS、新旧调度及发送前门；auto/fixed共享账号和授权/倍率回归通过。缺失适配的条件明确禁控。
4. D：相关测试、隔离PostgreSQL、浏览器两页交互/截图、性能、故障和旧版回退验证；逐场景绑定实际证据，不以本次文档检查充数。
5. E：后续实际账号小规模观察/校准及生产操作；不包含在当前“完成设计”范围内。

设计评审有D01–D09明确推荐值，代码已按本地实现授权落地；自动检测和调度控制默认关闭。生产迁移、真实账号检测、部署与启用另行授权。
